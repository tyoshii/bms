# BMS モダナイズ計画

## モダナイズ方針
- 既存機能（チーム・試合・成績・大会・Excel出力）を止めずに、段階的に刷新
- 「一括リプレイス」ではなく、`Strangler Fig`（新旧共存）でリスク最小化
- 優先順位は `セキュリティ > 運用安定性 > 開発速度 > UX改善`

## フェーズ1: 現状可視化と安全化（2〜4週間）
1. 依存関係・PHP/FuelPHPの既知脆弱性棚卸し（OAuth、SMTP、PHPExcel含む）
2. 本番監視の整備（アプリログ、DBスロークエリ、エラー通知）
3. バックアップ/リストア手順の検証と定期演習
4. 主要ユースケースの回帰テスト観点を作成（試合登録、成績入力、集計、エクスポート）

## フェーズ2: 実行基盤の更新（3〜6週間）
1. コンテナ/CIの標準化（Lint/Test/Buildを自動化）
2. DBマイグレーション運用を導入（スキーマ変更の手順化）
3. 秘密情報管理を環境変数/Secret Managerへ移行
4. Apache/PHP実行環境を段階更新（まず互換モードで安定化）

## フェーズ3: バックエンド再設計（6〜12週間）
1. ドメインを分割（Auth、Team、Game、Stats、Convention、Export）
2. APIファースト化（画面依存ロジックをサービス層へ分離）
3. 認証基盤更新（OAuth再実装、権限モデルの明文化）
4. 集計処理の最適化（重い統計クエリの再設計・インデックス整備）
5. Excel出力を `PHPExcel -> PhpSpreadsheet` 相当へ移行

## フェーズ4: フロントエンド刷新（6〜10週間）
1. Twig+jQuery画面を段階的にSPA/コンポーネント化（React等）
2. 主要画面から移行（成績入力、試合詳細、選手ページ）
3. スマホ最適化をレスポンシブ設計に統一
4. DataTables/Select2依存をUIコンポーネントへ置換

## フェーズ5: データ移行と本番切替（3〜6週間）
1. 新旧DB互換レイヤまたは双方向同期を設計
2. 段階リリース（機能フラグでチーム単位切替）
3. 並行稼働で整合性検証（成績集計結果の一致確認）
4. 旧機能停止とクリーンアップ

## 横断タスク（全フェーズ）
1. テスト戦略: 単体・API・E2E（回帰の自動化）
2. セキュリティ: RBAC、入力検証、監査ログ、レート制限
3. 品質指標: エラー率、平均応答時間、デプロイ頻度、MTTR
4. ドキュメント: 運用手順、障害対応、開発ガイド更新

## 推奨ターゲット構成（案）
- Backend: PHP 8.3 + 現行継続可能FW（段階移行）または Laravel/Symfony
- Frontend: React + TypeScript
- DB: MySQL 8.x
- Infra: Docker + CI/CD + AWS（監視/ログ統合）
- Auth: OAuth2/OIDC準拠

## 優先度の高いリスク
1. レガシー認証と権限の挙動差分
2. 成績集計ロジックの互換性崩れ
3. 大会/試合データの移行不整合
4. モバイル入力UXの劣化

## 最初の30日でやるべきこと
1. 現行機能の回帰テスト観点確定
2. 監視・ログ・バックアップの最低基準導入
3. DBマイグレーション運用開始
4. 成績入力APIの切り出し着手（最重要業務フローから）
