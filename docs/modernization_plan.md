# BMS リライト計画（2026）

## 前提
- 本計画におけるモダナイズは、既存アプリの部分改修ではなく**全面書き換えプロジェクト**を意味する
- **並行稼働は行わない**（新システムを完成後に切替）
- 大会機能（Convention）は新システムに実装しない（廃止）

## 目標
- UI/UX、アーキテクチャ、運用基盤、認証、開発体験を2026年水準へ刷新
- 野球成績管理の中核機能（チーム、選手、試合、打撃/投球成績、集計、Excel出力）を再設計
- セキュアかつ高速で、モバイル中心でも入力しやすいプロダクトへ再構築

## ターゲット技術スタック（2026）
- Frontend: `React 19` + `TypeScript` + `Next.js 16`（App Router, Server Components）
- UI: `Tailwind CSS v4` + `shadcn/ui` + `TanStack Table`
- Backend: `Java 21` + `Quarkus`（`quarkus-rest`, Validation, Security）+ `OpenAPI`
- DB: `PostgreSQL 17` + `Hibernate ORM with Panache` + `Flyway`
- Cache/Queue: `Redis`（`SQS` は後段の低優先度機能として導入）
- Auth: `Auth.js` + OAuth2/OIDC（Google）
- File Export: `ExcelJS`（xlsx出力）
- Infra: `AWS`（ECS/Fargate, RDS, ElastiCache, S3, CloudFront, WAF）
- Observability: `OpenTelemetry` + `Datadog` or `Grafana Cloud`
- CI/CD: `GitHub Actions` + preview環境 + 本番自動デプロイ
- OpenAPI運用: Backend は Code First（Java Interface/DTO 先行）で実装し、QuarkusのOpenAPI/Swagger UI拡張（`quarkus-smallrye-openapi`）で `openapi.yaml` を生成。Frontend は `openapi.yaml` からクライアント処理を実装

## アーキテクチャ方針
- APIファースト（OpenAPIを単一契約としてフロント/バックで共有）
- モジュラーモノリスで開始し、必要時にサービス分割
- プロトタイプ段階はオンライン集計を優先し、非同期再計算ジョブは後段導入
- 権限制御はRBACを明文化（管理者/チーム管理者/一般）
- BFF（Backend for Frontend）を採用し、画面要件に最適化したAPIを提供

## 機能スコープ（新システム）
- 実装対象
1. 認証/認可（メール/ソーシャルログイン、権限管理）
2. チーム管理
3. 選手管理
4. 試合管理
5. 成績入力（打撃/投球）
6. 統計ダッシュボード（チーム/個人）
7. Excelエクスポート（低優先度。初期リリース後の後段実装）

- 廃止対象
1. 大会管理（大会一覧、大会試合、大会成績、関連管理画面/API/テーブル）

## 実行計画（並行稼働なし）

### フェーズ0: プロジェクト起動（2週間）
1. 要件確定（新旧差分、廃止機能、非機能要件）
2. 画面一覧・遷移・情報設計を確定
3. 成果物定義（MVP/正式版、受け入れ基準、リリース基準）

### フェーズ1: 設計（4週間）
1. ドメイン設計（Team, Player, Game, Stats, Export, Auth）
2. DB論理/物理設計（PostgreSQL前提）
3. OpenAPI設計とエラーモデル標準化（Code First: Java実装から `openapi.yaml` を生成し、FEクライアント生成に利用）
4. デザインシステム設計（タイポ、カラー、コンポーネント、アクセシビリティ）
5. 監査ログ・セキュリティ設計（PII、権限、監査証跡）

### フェーズ2: 基盤構築（3週間）
1. リポジトリ/ビルド基盤構築（Frontend: `pnpm` / Backend: `Gradle`）
2. CI/CD・IaC・環境分離（dev/stg/prod）
3. 認証基盤・共通UI基盤・共通エラーハンドリング実装
4. 監視/通知基盤（APM, ログ, メトリクス, アラート）

### フェーズ3: アプリ実装（8〜12週間）
1. 認証・ユーザー/権限
2. チーム・選手管理
3. 試合登録・参加者管理
4. 成績入力UI（高速入力、バリデーション、下書き保存）
5. 統計画面（フィルタ、期間比較、ランキング）
6. 管理画面（運用者向け）

### フェーズ6: 後段機能（低優先度）
1. Excel出力（正式リリース後のスプリントで実装）
2. SQS を利用した非同期再計算ジョブ導入

### フェーズ4: 総合検証（4週間）
1. E2E/統合/負荷/セキュリティテスト
2. 既存データ移行リハーサル（複数回）
3. UAT（実ユーザー検証）
4. リリース判定

### フェーズ5: 本番移行（1週間）
1. 既存システム停止メンテナンス
2. 最終データ移行
3. 新システム切替
4. 初期監視強化（72時間）

### フェーズ7: 安定化（2〜4週間）
1. 障害/性能チューニング
2. UX改善の短期反映
3. 廃止機能導線の最終整理（大会機能完全撤去）

## データ移行方針（ワンショット移行）
- 並行稼働しないため、切替時に**一度だけ本番移行**を実施
- 変換対象
1. users, teams, players, games
2. stats_hittings, stats_pitchings, stats_players, games_runningscores
- 廃止対象
1. conventions, conventions_teams, conventions_games
- 移行手順
1. 凍結期間開始（旧システム更新停止）
2. エクスポート/変換/インポート
3. 件数整合性・集計整合性チェック
4. 問題なければ切替確定

## 品質基準（受け入れ）
- 可用性: 月間稼働率 99.9%以上
- 性能: 主要画面のp95応答 300ms以下（キャッシュ適用時）
- 品質: 重大バグ 0 件でリリース
- セキュリティ: 重大脆弱性 0 件（SAST/DAST依存）
- テスト: 主要業務フローE2Eカバレッジ 100%

## 主要リスクと対策
1. 移行日の障害
- 対策: リハーサル複数回、ロールバック手順、移行判定ゲート
2. 集計ロジック差異
- 対策: 旧システムとの比較ツールを事前実装
3. UI刷新による学習コスト
- 対策: 操作ガイド、オンボーディング、段階的ヘルプ表示
4. 大会機能廃止の業務影響
- 対策: 事前告知、代替運用定義、旧データ参照アーカイブ提供
